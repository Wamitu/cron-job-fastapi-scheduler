1 Project Overview

iParish CMS is a multi-tenant church management platform designed for the Catholic Diocese structure. It manages church parishes across three hierarchical access levels:

RoleScope
SysAdminFull platform access — no restrictions
BishopAll parishes within their assigned diocese
Priest / AdminTheir single assigned parish only

The system handles:

  • Member management (registration, groups, member numbers)
  • Sacrament records and certificate generation
  • Financial collections (offering, tithe, donations via cash/M-Pesa)
  • Fund project and fundraising tracking
  • Attendance tracking for parish events
  • Subscription billing per parish (plans, payments, lifecycle)
  • Bulk SMS and email communications
  • Full audit trail of all system operations

3 Local Development Setup

Prerequisites

  • Docker & Docker Compose
  • Python 3.11+ (only if running outside Docker)

Steps

# 1. Clone the repository
git clone <repo-url>
cd iparish-cms-fastapi-backend

# 2. Copy and configure environment variables
cp .env.example .env
# Edit .env with real values — see Section 4

# 3. Build and start all services
docker compose up --build

# API available at:   http://localhost:8000
# Swagger UI:         http://localhost:8000/docs
# ReDoc:              http://localhost:8000/redoc
ⓘ
On first startup, the app automatically seeds the database with default roles, a diocese, a parish, a SysAdmin user, sacrament types, subscription plans, and features.

Running Migrations Manually

docker exec -it iparish_web alembic upgrade head

7 Authentication & Authorization

Authentication

All protected endpoints require a Bearer JWT token in the Authorization header:

Authorization: Bearer <token>

Tokens are obtained via POST /user/login and expire after 360 minutes (6 hours).

Key functions in services/auth_service.py:

  • hash_password(password) — bcrypt hash
  • verify_password(plain, hashed) — compare plain vs hashed
  • create_jwt_token(data, expires_delta) — generate HS256 JWT
  • get_current_user(token, db) — FastAPI dependency for protected routes
⚠
The JWT secret is currently "my-secret-key". This is not suitable for production and must be rotated and stored as an environment variable before go-live.

Role-Based Access Control

RoleScope
SysAdminFull platform access — bypasses all scope checks
BishopAll parishes within their diocese only
PriestTheir assigned parish only
AdminAdministrative functions within their parish

Applied via decorator pattern:

@require_roles_by_titles("Priest", "Admin")
async def my_endpoint(parish_id: int, ...):
    ...

Priests and Bishops must always pass parish_id as a query parameter. The middleware validates the scope automatically.

Feature-Based Access Control

Some endpoints are gated by the parish's active subscription features (e.g., certificate_generation, member_management). This is checked in the feature middleware before the endpoint handler executes.

8 Subscription System

Parishes are billed via subscription plans. Each plan has a configurable set of enabled features.

Status Lifecycle

INACTIVE →
ACTIVE →
GRACE PERIOD →
EXPIRED →
INACTIVE
StatusMeaning
inactiveNo active subscription
activeValid subscription, within end date
grace_periodEnd date passed, within 3-day grace window
expiredGrace period ended (3+ days past end date)
cancelledManually cancelled

Status transitions are handled automatically by a daily Celery task at 10:00 AM UTC (see Section 9).

Subscription Changes

Planned plan changes (upgrades/downgrades) are stored in ParishSubscriptionChange and applied on the scheduled change date by the Celery task.

9 Background Tasks & Scheduling

Background tasks run on Celery with Redis as the broker. Scheduling is handled by Celery Beat.

update_subscription_statuses — Daily at 10:00 AM UTC

  • Transitions subscription statuses based on end_date
  • Applies pending subscription plan changes
  • Defined in core/tasks.py

send_bulk_sms_task(message, recipients, masked_number, telco)

  • Sends bulk SMS via Africa's Talking asynchronously
  • Triggered from the /communications endpoints
  • Defined in core/tasks.py

12 Bulk Upload System

The /bulk-upload router (api/bulk_upload_router.py) handles CSV imports for:

  • Members
  • Collections
  • Attendance records
  • Additional entities as implemented
ⓘ
All bulk upload routes require parish_id as a query parameter. The router validates, parses, and inserts records in bulk. Errors are returned per-row where applicable.

13 Logging & Audit Trail

Application Logs

Configured in log_config.py using Loguru:

  • Location: logs/{YYYY}/week_{WW}/system_{YYYY-MM-DD}.log
  • Rotation: Daily
  • Retention: 30 days
  • Compression: ZIP
  • Console format: JSON at INFO level

Audit Logs

Every mutating HTTP operation (POST, PUT, DELETE, PATCH) is automatically recorded in audit_logs with:

  • user_id, parish_id
  • HTTP method and path
  • Response status code
  • request_body — sensitive fields are redacted
  • before_data — record state before the change
  • after_data — record state after the change

Audit logs are viewable via GET /audit-log/all (SysAdmin only).

16 Known Constraints & Notes

⚠
JWT Secret is hardcoded — "my-secret-key" in services/auth_service.py must be moved to an env variable before any production deployment.
⚠
M-Pesa is not integrated — Mpesa payments are recorded manually. A separate STK push / callback integration would need to be built.
⚠
Live code mount in Docker — docker-compose.yml mounts .:/app for hot reload. This must be removed or conditionally applied for production.
⚠
Default DB credentials — Docker Compose uses fastapi_user:fastapi_password. These must be changed for any non-local environment.
ⓘ
Untyped JSON fields — member_data, data, parish_data, and parish_settings are flexible JSON columns. Schema changes here don't require migrations but require care when reading across code paths.
ⓘ
Seeding runs on every startup — The lifespan seed logic uses get-or-create patterns, so it is safe to run repeatedly, but it adds startup latency.
ⓘ
Celery Beat timezone — Beat scheduler runs in UTC. The daily subscription job fires at 10:00 AM UTC. Adjust if the target timezone differs.
ⓘ
Soft delete pattern — Most entities support soft deletion via is_archived=True. Always filter by is_archived=False in list queries unless intentionally including archived records.
